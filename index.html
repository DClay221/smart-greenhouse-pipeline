Project Overview

End-to-end IoT data
engineering in production style

The Smart Greenhouse Pipeline demonstrates the full modern data engineering stack — from edge device ingestion through real-time stream processing, dual-layer cloud storage, intelligent actuation logic, and live visualization.

A Raspberry Pi acts as the edge device, publishing six environmental sensor readings every 15 seconds via secured MQTT to AWS IoT Core. An MQTT-Kafka bridge forwards each message into Apache Kafka, where a Python consumer applies threshold evaluation, hysteresis-controlled actuation logic, and data quality validation before writing to both Amazon S3 and InfluxDB simultaneously. A Grafana dashboard powered by native Flux queries provides millisecond-latency live visualization. An OpenWeather API integration delivers tiered proactive briefing emails twice daily, distinguishing between today's operational window and the overnight period through a three-level urgency system.

System Design

Pipeline Architecture

A Lambda-style architecture runs real-time and batch storage layers in parallel, ensuring both low-latency querying and permanent archival without compromise.

Edge

Raspberry Pi — Sensor Simulation

Python script generates realistic sensor readings with gradual drift behavior, validates against physically possible ranges, and publishes to AWS IoT Core every 15 seconds via MQTT with mutual TLS certificate authentication.

Python 3.12 AWS IoT SDK MQTT TLS Certificates
Ingestion

AWS IoT Core — Managed MQTT Broker

Receives and routes secured MQTT messages from registered IoT Things. An MQTT-Kafka bridge script subscribes to the sensor topic and forwards each message into the local Kafka cluster with full acknowledgement.

AWS IoT Core IoT Policy Thing Registry QoS AT_LEAST_ONCE
Streaming

Apache Kafka — Stream Processing

Three-partition Kafka topic ingests sensor payloads. A Python consumer group evaluates thresholds with consecutive breach counting, triggers hysteresis-controlled actuator responses, and writes to both storage layers before processing alerts.

Apache Kafka kafka-python Docker Consumer Groups
Storage

Dual-Layer Storage — S3 + InfluxDB

Every validated reading is written simultaneously to Amazon S3 as a date-partitioned JSON file (permanent raw archive) and to InfluxDB as a tagged time-series point (millisecond-latency queries). Actuation events are logged to a separate S3 prefix for full audit trail.

Amazon S3 InfluxDB 2.7 Flux Query Language Date Partitioning
Actuation

ActuatorManager — Device Control Layer

Manages nine simulated greenhouse devices with per-device minimum run times, hysteresis enforcement, and shared state written to disk on every evaluation cycle for consumption by the API server.

Hysteresis Control Minimum Run Times State Persistence S3 Audit Logging
Alerting

Amazon SNS + Gmail SMTP — Dual Alert Channels

Amazon SNS handles real-time threshold breach notifications with debouncing to prevent alert fatigue. Gmail SMTP delivers rich HTML briefing emails at 7 AM and 7 PM with tiered forecast windows and urgency-scored proactive recommendations.

Amazon SNS Gmail SMTP Alert Debouncing HTML Email
Visualization

Grafana — Live Dashboard

Native InfluxDB data source with Flux queries provides millisecond-latency updates across twelve panels — six time-series trend panels and six current-value stat panels — plus an actuator status table showing real-time device states.

Grafana 10.2 Flux Queries Threshold Coloring Docker
Weather

OpenWeather API — Proactive Intelligence

Polls current conditions and 48-hour forecast every 10 minutes. Splits forecast into two operational windows with three urgency levels: Routine, Advisory, and Urgent. Urgent conditions trigger immediate alerts independent of the briefing schedule.

Development

Build Phases

The project was built incrementally across ten planned phases, each adding a distinct layer of production-grade capability.

  • 1
    Complete

    Ingest — Sensor Simulator and AWS IoT Core

    Python sensor simulation on Raspberry Pi publishing six environmental metrics every 15 seconds via secured MQTT with mutual TLS certificate authentication to AWS IoT Core.

  • 2
    Complete

    Stream — Apache Kafka and Real-Time Alerting

    MQTT-Kafka bridge forwards messages into a local Kafka topic. Python consumer evaluates thresholds with consecutive breach counting, debouncing, and Amazon SNS email alerts.

  • 3
    Complete

    Store — Amazon S3 Data Lake

    Every validated sensor reading written to S3 as a date-partitioned JSON file, forming a permanent queryable raw data archive for long-term storage and future analytics.

  • 4
    Complete

    Visualize — Grafana Dashboard

    Initial live sensor dashboard built with Grafana and the Infinity plugin, served via a Python REST API reading from S3. Later superseded by the InfluxDB-native dashboard in Phase 9.

  • 5
    Complete

    Hardening — Production Readiness

    Centralized configuration module, data quality validation, exponential backoff reconnection logic, alert debouncing, hysteresis controls, and GitHub repository setup with proper credential exclusion.

  • 6
    Complete

    Actuation — Device Simulation Layer

    ActuatorManager controls nine simulated greenhouse devices with configurable minimum run times, hysteresis enforcement, real-time state sharing between processes, and full actuation event logging to S3 for audit trail.

  • 7
    Complete

    Weather — OpenWeather API Integration

    Tiered forecast windows split into Today and Tonight/Tomorrow AM operational periods with three-level urgency scoring. Scheduled HTML briefing emails at 7 AM and 7 PM via Gmail SMTP. Urgent conditions trigger immediate alerts independent of the schedule.

  • 9
    Complete

    Time-Series — InfluxDB Integration

    InfluxDB 2.7 added to Docker Compose alongside Kafka and Grafana. Kafka processor writes to InfluxDB in real time alongside S3. Grafana dashboard migrated to native Flux queries with millisecond latency, replacing S3 polling overhead.

  • 8
    Pending

    AWS Kinesis — Cloud-Native Stream Processing

    Kinesis Data Streams planned as a cloud-native replacement for Apache Kafka. Currently unavailable on this AWS account tier. Architecture is fully documented and ready for implementation when account activation is resolved.

  • 10
    Planned

    Predictive Analytics — NOAA Data and scikit-learn

    ML pipeline using NOAA historical climate data combined with collected greenhouse sensor readings to train a scikit-learn model predicting indoor conditions from outdoor weather forecasts. Planned for implementation as sensor data accumulates.

Engineering Decisions

Challenges and Solutions

Real engineering problems encountered and solved during development. These represent the practical reality of building production-style systems rather than tutorial projects.

S3 Pagination Performance

The sensor API hung for 18 minutes because list_objects_v2 with MaxKeys scanned from the bucket root alphabetically, returning the earliest files rather than the most recent. Fixed by constructing date-prefixed S3 paths to scope every query to today's partition only.

Inter-Process State Sharing

The Kafka processor and API server are separate processes with independent ActuatorManager instances. Grafana displayed stale actuator states because the API's instance was never updated. Solved by writing state to a shared JSON file on every evaluation cycle.

SNS Free Tier Exhaustion

Five-second sensor intervals triggered an alert on every threshold breach, exhausting 1,000 monthly SNS notifications within days. Solved with consecutive breach counting — alerts only fire after three sustained readings — and a reading interval increase to 15 seconds.

AWS Service Restrictions

Kinesis Data Streams and Timestream for LiveAnalytics were unavailable on a new AWS account. Replaced with Apache Kafka in Docker and InfluxDB respectively — both industry-standard tools with skills that transfer directly to their AWS counterparts.

Weather Forecast Window Accuracy

OpenWeather forecast intervals extending into the next day caused false proactive alerts on clear days. Solved with a tiered window system splitting forecasts into distinct Today and Tonight/Tomorrow AM operational periods with independent evaluation.

Actuator Hysteresis Design

Sensors drifting near thresholds caused actuators to cycle on and off rapidly — a realistic problem in real greenhouse and HVAC systems. Implemented minimum run time enforcement per device and consecutive breach counting before any actuation is permitted.
